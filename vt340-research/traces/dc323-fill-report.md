# DC323 fill and hole-fill first implementation

## Evidence policy

The DEC *Dragon Video System Hardware Specification* is used as a hypothesis
source, not as an infallible oracle. The document is known to contain errors,
and several advanced fill cases depend on subtle state carried between
commands. This implementation therefore requires agreement among:

1. a documented register/command interpretation;
2. native firmware command provenance where the firmware exercises the case;
3. a small pixel-level regression with an unambiguous result.

Unconstrained edge cases are left unimplemented rather than extrapolated.

Primary reference:
[Dragon Video System Hardware Specification (1985)](https://archive.computerhistory.org/resources/access/text/2021/02/102739869-05-01-acc.pdf),
sections 3.5.1.1.1, 3.7.3, and 4.1.1.2.

## Corrected mode decode

The mode register's low two bits decode as:

| Bits | Mode |
| ---: | --- |
| `00` | normal |
| `01` | reserved |
| `10` | linear pattern |
| `11` | fill |

This corrects the earlier project checklist, which had mistakenly described
`01` as fill and `11` as unresolved. In fill mode, bit 2 chooses X/Y fill,
bit 3 selects baseline fill, bit 4 enables hole fill, and bit 7 enables
writing. The raster command must enable the destination; source 1 is used as
the B-edge address generator and must not be enabled as a bitmap source.

## Implemented first slice

`dc323_device::execute_fill` implements deliberately simple cases:

- two-edge X fill when the A and B Bresenham paths advance on matching Y
  coordinates;
- two-edge Y fill when they advance on matching X coordinates;
- X/Y baseline fill using the applicable source origin as the fixed baseline;
- equal-duration X/Y edge-pair chains, retaining each edge endpoint as the
  next command's origin until a destination-origin load or mode change;
- tiled and untiled source-2 patterns across ordinary and baseline fill spans;
- signed Error 1/Error 2 initialization adjustments for edges A and B;
- inclusion of both edge pixels in each fill scan; and
- exclusion of each edge vector's endpoint, matching ordinary vector rules.

The focused regression covers a 5-by-4 X fill, a 4-by-5 Y fill, and a sloped
edge filled to each of the vertical and horizontal baseline forms. Paired
commands form small X-fill and Y-fill diamonds to verify endpoint continuation,
and an explicit destination-origin load verifies that a new string restarts.
The regression also checks that reserved mode `01` produces no drawing.

For normal-mode, destination-only broad parallelograms, hole fill preserves
all writes generated by the original fast/slow paths—including duplicate
writes—and adds only absent pixels between the first and last selected pixel
on each occupied bitmap scanline. A rotated `(4,2)` by `(-2,4)` regression
proves that holes remain with mode `0080` and that mode `0090` repairs two
specific interior gaps.

## Deliberate limits

The following are not claimed by this round:

- source-1-coupled hole filling, because the correct source address for an
  added destination pixel has not been established;
- holding one edge after it expires while the other continues;
- continuation when paired edges have unequal durations, which requires
  preserving partial generator state rather than just completed endpoints;
- crossing-edge reversal behavior;
- complement-mode doubling detection or firmware-directed tripling;
- proof that horizontal scanline gap repair exactly matches every DC323B
  internal hole-fill case.

These cases need native command traces and, where possible, comparison with
known hardware output before implementation.

## Native ReGIS probe

`fixtures/regis-fill.regis` sends one ReGIS `F(V...)` rectangle through the
ordinary Comm 1 PTY path. The terminal drew the expected 200-by-100 filled
rectangle, but the exact DC323 mode inventory contained only `0080` and
`00c0`; no mode with low bits `11` was submitted. The firmware implements this
ReGIS polygon as a series of normal-mode spans rather than using DC323 fill
mode.

This is useful negative evidence: ordinary ReGIS `F(...)` is not a native
fill-mode validation. Until another firmware path is found, fill mode must be
tested with the firmware-free device harness and treated as specification-led
rather than VT340-firmware-confirmed.

## Verification

- The firmware-free `dc323test` build and regression pass with the new X/Y,
  baseline, paired-edge chaining, restart, error-offset, source-2 pattern, and
  hole-fill cases.
- The VT340 target builds successfully.
- The optional fast-start native boot regression passes.
- The 130-second native graphics raster-command regression passes unchanged.
- The native ReGIS fixture renders its filled rectangle and confirms that this
  firmware path does not issue DC323 fill-mode commands.
