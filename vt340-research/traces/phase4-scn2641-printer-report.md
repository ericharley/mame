# SCN2641 printer diagnostic investigation

## Pre-fix root cause

The first observed failure in the native CPU1 printer diagnostic is an address
decode error in the VT340 driver, before any transmitted character can be
evaluated.

CPU1 enters the diagnostic at `F6F0`.  The first loopback iteration reads the
SCN2641 status register at `F001` from `F763-F766`; the branch at `F767`
requires status bit 0 (`TxRDY`) to be set.  The observed value is `00`, so the
branch reaches `F7A2`, sets `F0`, and the caller reaches `F729`, where result
bit 6 is set.  This is the source of `VT340 Printer Port Error - 7`.

Before correction, the driver mapped the SCN2641 only at `F058-F05B`.  The firmware uses
the complete `F000-F03F` aperture, with A1:A0 selecting the four registers:

| Address low bits | Read | Write |
| --- | --- | --- |
| `00` | receive holding register | transmit holding register |
| `01` | status register | SYN register |
| `10` | mode register 1/2 | mode register 1/2 |
| `11` | command register | command register |

VT340 schematic sheet 8P0 connects CPU1 AA1 and AA0 directly to E81's A1 and
A0 inputs.  The E78 PAL equation for `2641SEL L` selects the lower 64 bytes of
the CPU1 I/O page (`F000-F03F`) for either read or write.  The adjacent upper
64 bytes (`F040-F07F`) select E61, the SCN2681 DUART.  The existing `F058`
mapping is therefore inside the DUART aperture and cannot represent E81.

This explains the exact observed value: the `F001` access falls through to
shared RAM, whose reset value is zero, so the firmware sees `TxRDY=0` without
the SCN2641 receiving any of the setup writes.

## Native firmware path

The relevant path is:

```text
F6F0 printer diagnostic
  F6F2 write CR=B7 to F013
  F6FA call F749 (configuration sweep)
	    F7C5 advance the mode pointer and write MR2 through F012
	    F7E7 reset the mode pointer and write MR1 through F012
    F760 run one local-loopback transfer
      F818 update command through F013
      F763 read SR at F001
      F767 require TxRDY (SR0)
      F76A write THR at F010
      F77B read SR at F001
      F77F require RxRDY (SR1)
      F782 require PE/OE/FE clear (SR3-SR5)
      F786 read RHR at F000
      F789 compare received character
  F703 branch on F0
  F729 set POST result bit 6 on failure
```

The pre-fix trace is generated by
`phase4-scn2641-printer-diagnostic.lua`.  It records entry at emulated time
122.241934 seconds, setup writes to `F013` and `F012`, and the failing `F001`
read of `00`.

## Initial configuration decode

The first observed configuration is:

- MR1 `CA`: asynchronous 16X mode, 7 data bits, parity disabled, and two stop
  bits.
- MR2 `71`: baud selector 1 (75 baud with a 3.6864 MHz BRCLK), internal
  transmitter and receiver clocks, and 16X clock outputs.
- CR `B7`: local loopback, RTS asserted, reset error flags, receiver enabled,
  DTR asserted, and transmitter enabled.

In local loopback the datasheet specifically requires CR0 (TxEN), CR1 (DTR),
and CR5 (RTS) to be one; CR2 (RxEN) is ignored.  The chip internally connects
RTS to CTS, transmitter data to receiver data, and the transmitter clock to
the receiver clock, while external CTS, DCD, and RxD are ignored.  In normal
mode the VT340 schematic permanently asserts the active-low CTS and DCD pins
by grounding them; the driver now models those physical levels.

The order matters.  `F7C5` reads the command register to reset the mode
pointer, reads MR1 to advance the pointer, and writes `71` to MR2.  `F7E7`
then reads the command register again and writes `CA` to MR1.

The post-decode trace exposes a second, device-level root cause.  MAME's
shared PCI/EPCI implementation applies an undocumented SCN2651-family quirk
on every MR1 write: it copies the old MR1 value into MR2.  The comment says
this was verified on hardware, but the code also applies it to the distinct
asynchronous-only SCN2641.  Thus the later MR1=`CA` write silently replaces
the intended MR2=`71` with reset value `00`, disables the internal baud-rate
generator, and leaves the transmitted character in the holding register.
The resulting status is `C0`: neither `TxRDY` nor `RxRDY` can advance.  The
SCN2641 programming specification documents independent MR1/MR2 accesses and
does not document this transfer.  The native VT340 sequence also depends on
MR2 retaining its value across a later MR1 write.

After retaining MR2, the first character progresses but is initially received
as `4C` with framing error (`SR=E3`) rather than the transmitted `0A`.  The
bit trace shows why: while MR1 still contains its reset value `00`, the shared
implementation interprets it as the PCI/EPCI synchronous mode and emits a
stream of zero-valued SYN fill characters.  Those bits leave the transmitter
state machine mid-character when the firmware disables it and loads the first
valid asynchronous MR1 value.

That behavior cannot apply to the SCN2641.  It is asynchronous-only, its MR1
table defines `MR1[1:0]=00` as invalid, and the specification states that a
reset clears the registers and leaves the part idle until appropriate control
words initialize it.  The ACI transmitter and receiver must therefore remain
idle while the mode field is invalid; it must not enter the shared PCI/EPCI
synchronous state machine.

The SCN2641 specification says local loopback connects transmitter output to
receiver input, RTS to CTS, and clocks the receiver from the transmitter
clock.  It also ignores external CTS, DCD, and RxD.  Consequently the shared
`device_serial_interface` parity correction used by the SCN2681 does not
apply: `scn2641_device` has its own bit-level transmitter, receiver, and parity
state machine in `scn_pci.cpp`.

The smallest shared-device correction is to (1) limit the verified MR1-to-MR2
transfer quirk to the PCI/EPCI variants and retain MR2 on an SCN2641 MR1
write, and (2) keep an uninitialized SCN2641 serializer idle while the invalid
mode field is zero.  This preserves all clock-source, framing, parity, and
local-loopback semantics rather than forcing status bits or manufacturing a
received character.

The audit also found that the implementation cleared CR4 only in a temporary
function argument after latching the command.  The specification defines
reset-error as a one-time command with no internal latch, so the stored
command now clears CR4.  This does not manufacture diagnostic success; it
makes subsequent command-register reads return `A7`/`A2` rather than retaining
the written `B7`/`B2` reset request.

## Corrected execution

The corrected native diagnostic performs 18 complete loopback transfers.  At
every iteration the status sequence is `C1` before the THR write and `C7`
after serialization.  The firmware masks `SR5:SR3` and observes `00`, so
framing, overrun, and parity error are all clear.  The SCN2641 has a
single-character receive holding register rather than a FIFO; every RHR read
consumes the character and clears `RxRDY` before the next iteration.

| Sweep | MR2 | MR1 values | Transmit / receive values |
| --- | --- | --- | --- |
| Baud-rate sweep | `71 72 74 75 76 77 7A 7C 7E` | `CA` | `0A/0A 14/14 28/28 50/50 A0/20 41/41 82/02 05/05 0A/0A` |
| Format sweep | `7F` | `4A 7A 5A 4E 4E 4E 7E 5E CA` | `14/14 28/28 50/50 A0/A0 41/41 82/82 05/05 0A/0A 14/14` |

The apparent differences `A0/20` and `82/02` are the expected seven-bit
masking under MR1=`CA`; the firmware applies the same mask before comparing.
The format sweep covers seven- and eight-bit characters, odd/even/no parity,
one and two stop bits, and the supported asynchronous clock factors.  The
baud sweep selects 75, 110, 150, 300, 600, 1200, 2400, 4800, 9600, and (in
the format sweep) 19200 baud from the internal 3.6864 MHz BRCLK.

The first corrected transfer is:

```text
122.278574  SR read before THR       C1
122.278583  THR write                0A
122.469818  SR read after loopback   C7
122.469823  masked error bits        00
122.469884  RHR read                 0A
```

After the eighteenth transfer, CPU1 reaches the normal return at `F725`
without visiting `F7A2` or `F729`.  At `123.960841` seconds the POST result
submitted with command 32 is `00`, rather than the former printer-error value
`40`.

The focused regression is `tests/phase4-scn2641-printer.sh`.

## Full POST and screen result

A 180-second cold boot reaches the native normal transition at emulated time
`123.960606` and submits command 32 with result `00` at `123.960841`.  The
firmware-generated success panel contains `VT340 OK`; no NVR, Comm 1, Comm 2,
or printer error text remains.

The printer-port acceptance result is exact and repeatable, but the broader
display path still has a separate persistence defect.  The old top-left
`Wait` glyph is not erased, and snapshots at 130 and 140 seconds omit the main
success panel before it reappears at 160 and 180 seconds.  This is not a POST
or SCN2641 regression—the result stays `00` and the original firmware has
submitted the success display—but it remains open renderer/display-state work.

The final regression set passed:

- `phase4-scn2641-printer.sh`
- `phase4-scn2681-loopback.sh`
- `phase4-e80-post.sh`
- `phase4-pbt-transfer.sh`
- `phase4-ring-drain.sh`
